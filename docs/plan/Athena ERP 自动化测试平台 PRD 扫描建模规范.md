# PRD 统一扫描、解析与测试建模规范

版本：V1.0  
适用范围：Athena ERP 自动化测试平台全部业务模块。

## 1. 目标

将分散的 PRD 文件转换成统一、可追溯、可关联、可供测试设计引擎读取的业务知识模型。用户不需要逐份上传 PRD；Codex 应递归扫描项目本地 PRD 目录。

## 2. 输入目录与文件策略

默认输入：`prd/`，递归扫描子目录。

建议目录：
```text
prd/
├── 基础资料/
├── 采购/
├── 销售/
├── 库存/
├── 生产/
├── 委外/
├── 财务/
└── 其他/
```

第一阶段必须支持：
- Markdown：`.md`、`.markdown`
- 纯文本：`.txt`
- JSON：`.json`（用于已有结构化资料）

预留插件支持：
- Word：`.docx`
- Excel：`.xlsx`、`.xls`
- PDF：`.pdf`
- 图片：`.png`、`.jpg`、`.jpeg`

不支持的格式不得静默忽略，必须写入扫描报告并说明原因。扫描器不得修改原始 PRD。

## 3. 文档登记与版本识别

每份文档生成稳定 `document_id`，登记：
- 原始文件路径、文件名、文件哈希。
- 标题、业务模块、业务对象。
- 文档版本、发布日期、文档状态（如可识别）。
- 解析器版本、扫描时间。
- 文档间替代、引用、关联关系（如可识别）。

版本识别优先级：
1. 文档正文明确的版本字段。
2. 文件名版本标识。
3. 文档元数据。
4. 无法识别时标记 `UNKNOWN`，不得猜测。

同一业务对象存在多个版本时：
- 全部保留登记。
- 根据明确版本信息标注候选最新版本。
- 不删除旧版知识。
- 版本差异进入报告。
- 若无法判断生效版本，进入 `OPEN_QUESTIONS.md`。

## 4. 统一知识对象

必须支持以下实体：

| 对象 | 用途 |
|---|---|
| Document | PRD 文档登记 |
| Entity | 业务实体，如采购订单、供应商、品号 |
| Page | 页面、列表、编辑页、弹窗、页签 |
| Field | 字段及其属性 |
| Control | 输入框、下拉、开窗、日期、表格等控件 |
| Rule | 字段校验、业务规则、状态规则、计算规则 |
| Action | 新增、编辑、删除、审核、撤审、取单等动作 |
| Workflow | 多单据业务流程 |
| Dependency | 主数据、来源单据、上下游依赖 |
| Scenario | 测试场景草案 |
| Evidence | 原文位置、章节、表格或段落证据 |
| OpenQuestion | 缺失、歧义、冲突和待确认问题 |

## 5. 规则来源分类

每条规则必须标记 `source_type`：

- `PRD_EXPLICIT`：PRD 明确写出。
- `PRD_DERIVED`：根据多个明确内容推导，必须写出推导依据。
- `PLATFORM_SERVICE`：PRD 声明由平台服务或公共服务处理。
- `UI_OBSERVED`：仅从页面实际行为观察到。
- `USER_CONFIRMED`：用户或业务人员明确确认。
- `PENDING`：尚未确认。

禁止将 `PRD_DERIVED`、`UI_OBSERVED` 或 `PENDING` 改写成 `PRD_EXPLICIT`。

## 6. 页面与字段建模

页面至少提取：
- 页面名称、页面类型、所属业务对象。
- 页面入口或菜单路径（如果 PRD 有说明）。
- 页面区域、页签、工具栏、列表和弹窗。
- 页面操作及操作结果。

字段至少提取：
- 字段名称、业务含义、所属实体和页面。
- 是否必填、是否只读、是否可编辑。
- 数据类型、长度、精度、默认值、枚举值。
- 是否关联基础资料。
- 是否支持开窗选择、模糊查询、下拉选择。
- 字段联动、计算规则、校验规则。
- 规则来源和证据位置。

字段联动需结构化表达：
`触发字段 → 触发条件 → 目标字段 → 变化行为 → 预期结果`。

控件分类建议：
`TEXT_INPUT`、`NUMBER_INPUT`、`DATE_PICKER`、`DROPDOWN`、`LOOKUP`、`TREE_SELECT`、`CHECKBOX`、`RADIO`、`GRID`、`BUTTON`、`TAB`、`MODAL`、`UNKNOWN`。

若 PRD 仅描述字段但未说明控件行为，控件类型标记 `UNKNOWN`，后续通过 UI 探索补充。

## 7. 业务规则分类

至少支持：
- 必填与非空规则。
- 唯一性规则。
- 格式、长度、精度规则。
- 字段间联动规则。
- 默认值规则。
- 数据范围与权限规则。
- 数量、金额、税率、汇率等计算规则。
- 单据状态与状态迁移规则。
- 审核、撤审、过账规则。
- 来源单据取单规则。
- 已执行数量、未执行数量、占用数量规则。
- 删除限制与反向操作规则。
- 跨单据一致性规则。

每条规则必须有唯一 ID、规则描述、适用对象、触发时机、条件、预期结果、来源类型、证据引用、置信状态和待确认事项。

## 8. 单据状态与操作

状态机建模必须区分：
- PRD 明确状态。
- PRD 明确允许的状态迁移。
- 页面实际观察到的状态。
- 推导出的状态关系。

每个迁移包含：
`from_status`、`action`、`to_status`、`preconditions`、`effects`、`source_refs`。

若 PRD 未说明撤审条件、删除条件或过账条件，不得自行补齐。

## 9. 上下游业务流程与依赖

流程必须表达：
- 起点和终点。
- 单据节点。
- 节点间关系。
- 来源字段与目标字段映射（仅在资料明确时）。
- 数量口径（如订单数量、已到货数量、未到货数量）。
- 取单、回写、占用、释放等行为。
- 每个关系的证据与来源类型。

不得把某个模块的流程模板强加给其他模块。

## 10. 测试场景建模

每个场景至少包含：
- `scenario_id`
- 标题、所属模块、业务对象。
- 测试目标。
- 场景类型。
- 前置条件。
- 测试数据需求。
- 操作步骤草案。
- 预期结果与断言点。
- 关联规则 ID。
- 关联文档及证据。
- 自动化可行性：`UI_READY`、`NEEDS_UI_EXPLORATION`、`NEEDS_CONFIRMATION`、`NOT_UI_OBSERVABLE`。

场景类型：
- 正向流程
- 反向校验
- 边界值
- 必填校验
- 字段联动
- 状态迁移
- 上下游关联
- 数量与金额
- 权限与数据范围
- 异常恢复
- 回归

测试场景只能作为草案生成。规则未确认、前置数据不明或断言不可观察时，不得标记为可直接执行。

## 11. 证据追溯

所有解析结果应尽可能记录：
- `document_id`
- 原始文件路径
- 章节标题
- 页码（适用时）
- Markdown 行号或段落索引
- 原文摘录（短片段）
- 文档版本和哈希

没有证据的推断必须明确标记为推导，并写出推导链。不能定位证据时标记 `EVIDENCE_MISSING`。

## 12. 冲突与问题管理

必须识别：
- 同一字段多版本定义不一致。
- 同一规则多文档描述冲突。
- 页面描述与流程描述冲突。
- 缺少上下游字段映射。
- 状态迁移不完整。
- 控件行为不明确。
- PRD 声明平台服务执行但无可观察结果。
- 场景无法形成可靠断言。

输出 `OPEN_QUESTIONS.md`，每项包含问题、涉及文档、冲突证据、影响、建议确认对象和状态。

## 13. 解析质量分级

- `CONFIRMED`：原文明确且证据可定位。
- `DERIVED`：有明确推导链。
- `AMBIGUOUS`：原文存在歧义。
- `CONFLICTED`：不同来源冲突。
- `MISSING`：缺失。
- `UNSUPPORTED_FORMAT`：当前解析器不支持。

不得为了提高解析完整率而降低证据标准。

## 14. Codex 标准处理流程

1. 扫描目录并生成文件清单、哈希和文档登记表。
2. 识别标题、版本、模块、对象。
3. 解析页面、字段、控件、规则、动作和流程。
4. 生成统一 JSON 模型并通过 Schema 校验。
5. 建立实体、规则、流程和依赖关联。
6. 执行重复、冲突、缺失、证据和版本检查。
7. 生成测试场景草案、覆盖率矩阵和分析报告。

## 15. 第一阶段验收标准

- 能递归扫描 PRD 目录。
- 新增文件可被增量发现。
- 原始文件不被修改。
- 文档版本、哈希和路径可追踪。
- 结构化模型通过 Schema 校验。
- 每条规则可追溯来源或明确标记推导。
- 冲突和缺失进入待确认清单。
- 能形成实体、规则、流程、依赖和场景之间的关联。
- 能生成需求/规则/场景覆盖率报告。
- 解析失败不导致整个批次静默中断。
- Phase 1 不连接 ERP、不执行 Playwright。
