# 03 核心数据契约

> 以下为平台首版逻辑契约。Codex 应结合现有代码选定 YAML/JSON/Pydantic/TypeScript schema 等实现方式，但不得改变核心语义而不记录架构决策。

## 1. Module Manifest

每个业务模块必须有 `module.yaml`：

```yaml
schema_version: "1.0"
module:
  id: purchase
  name: 采购管理
  version: "0.1.0"
  status: draft
  owner: qa
  description: Athena ERP 采购模块自动化测试资产
compatibility:
  platform_api: ">=1.0.0 <2.0.0"
sources:
  prd_index: source-index/index.yaml
assets:
  knowledge: knowledge/
  page_mappings: page-mappings/
  scenarios: scenarios/
  testcases: testcases/
  data_recipes: data-recipes/
  test_suites: test-suites/
```

## 2. 场景 Scenario

字段至少包括：
- `id`：全局唯一；
- `module_id`；
- `title`；
- `business_goal`；
- `source_refs`：PRD/规则/页面证据引用；
- `preconditions`；
- `business_flow`；
- `risk_level`；
- `status`：draft/reviewed/approved/deprecated；
- `tags`。

## 3. 测试用例 Test Case

字段至少包括：
- `id`、`module_id`、`version`；
- `title`、`objective`；
- `scenario_refs`、`source_refs`；
- `preconditions`；
- `data_recipe_refs`；
- `dependencies`；
- `steps`；
- `assertions`；
- `cleanup_policy`；
- `status`；
- `timeout`、`retry_policy`。

每个正式用例至少包含一个可观察断言；每条断言必须引用业务规则、PRD 或批准的测试设计依据。

## 4. Step 动作类型

首版建议支持：
- `navigate`：导航到菜单/页面；
- `search`：列表查询；
- `open_record`：打开记录；
- `select_master_data`：通过 UI 搜索选择客户、供应商、品号、仓库、人员、部门等基础资料；
- `fill`：填写字段；
- `select_option`：选择下拉/单选项；
- `upload`：上传附件；
- `save`：保存；
- `submit`：提交；
- `approve`：审核；
- `unapprove`：撤审；
- `delete`：删除；
- `assert_visible`、`assert_text`、`assert_value`、`assert_row`；
- `capture_evidence`。

动作必须有页面映射、超时、失败信息和证据策略。不得允许模型输出任意 JS 并直接执行。

## 5. Page Mapping

页面映射描述页面路由、菜单路径、关键控件、定位优先级、等待条件和控件类型。定位优先级建议：
1. `getByRole` / accessible name；
2. `getByLabel`；
3. `getByPlaceholder`；
4. 稳定 `data-testid`；
5. 经验证的 CSS；
6. XPath 仅作为最后手段。

每个定位器应支持唯一性检查；定位结果不唯一时应失败并输出诊断，不能随意取第一个。

## 6. Data Recipe

数据配方描述如何通过 UI 准备前置数据：
- `entities`：供应商、品号、仓库、部门等；
- `create_order`：创建顺序；
- `references`：主从关联；
- `uniqueness_strategy`：测试编号前缀/时间戳/运行 ID；
- `reuse_policy`：never / within_run / approved_shared；
- `cleanup`：保留、撤审后删除、仅标记待清理等；
- `rollback_notes`；
- `assertions`：数据创建成功的 UI 验证。

数据准备必须幂等：重复执行时应能识别本次运行已创建的数据，避免重复造数。默认不复用共享业务数据，除非明确批准。

## 7. Dependency Graph

依赖关系必须是显式有向边：
- 用例依赖用例；
- 数据实体依赖数据实体；
- 集成步骤依赖模块用例或业务动作。

引擎必须检测循环依赖、缺失节点和跨模块版本不兼容。执行前输出拓扑顺序和阻塞原因。

## 8. Assertion

首版支持 UI 可观察断言：
- 页面/提示是否出现；
- 单据状态文本；
- 列表行是否存在；
- 字段值；
- 单据编号；
- 关键汇总值；
- 上下游单据关联信息（页面可见时）。

断言必须明确：观察位置、预期值/规则、等待策略、失败消息、来源依据。报告中保存断言实际值、预期值和截图/trace 引用。

## 9. Execution Result

执行状态统一为：
- `passed`
- `failed`
- `blocked`
- `skipped`
- `cancelled`
- `error`

报告必须区分：
- 测试步骤失败；
- 数据准备失败；
- 环境/登录失败；
- 断言失败；
- 平台异常；
- 人工阻塞。

## 10. 版本规则

- 平台核心、模块包、集成包独立版本化。
- 采用语义化版本。
- 破坏性 schema 变更必须升级主版本，并提供迁移器。
- 每份报告固定记录所使用的版本组合。
- 不允许运行时静默加载不兼容资产。
