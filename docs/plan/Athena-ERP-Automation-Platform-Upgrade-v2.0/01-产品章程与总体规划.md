# 01 产品章程与总体规划

## 1. 产品定位

建设一套面向 Athena ERP 的、基于浏览器真实用户操作的自动化测试平台。平台能够读取业务需求资料，形成业务知识模型、测试场景、测试用例和依赖关系，自动准备测试数据，驱动 ERP 页面执行操作，校验业务结果并输出可追溯报告。

它不是：
- 采购模块的专用脚本；
- 仅负责录制和回放的 Playwright 脚本库；
- 通过数据库或 API 绕过 UI 的接口测试框架；
- 每新增一个模块就复制一套 Phase 1 到 Phase 6 的独立项目。

## 2. 最终业务目标

用户可以选择：
- 单模块测试：采购、销售、库存、应收、应付、生产等；
- 跨模块集成测试：采购到应付、销售到应收、采购到库存等；
- 回归测试：指定模块、业务链路或版本范围；
- 指定测试范围：场景、测试套件、用例、组织、账套和测试数据范围。

平台输出：
- 测试执行报告；
- 通过/失败/阻塞/跳过统计；
- 断言结果与证据；
- 业务流程覆盖率；
- 缺陷线索和失败定位；
- 测试数据创建与清理记录；
- 可复跑的执行配置和版本信息。

## 3. 设计原则

### 3.1 平台与业务分离
平台核心只实现通用机制。业务模块的字段、流程、规则、页面映射、测试场景和数据配方放在模块包中。

### 3.2 配置优先，代码扩展受控
优先通过 YAML/JSON/Markdown 等可审查资产描述模块差异。只有出现稳定、可复用且配置无法表达的行为时，才增加适配器代码。

### 3.3 业务知识可追溯
每条正式用例必须能追溯到 PRD、业务规则、页面行为或明确批准的测试设计依据。不得让模型凭空编造业务规则。

### 3.4 UI 是当前唯一业务操作通道
登录、查询、选择基础资料、录入、保存、审核、撤审、删除、单据流转均通过 Playwright UI。禁止以 SQL、OpenAPI、MCP 作为测试数据准备或业务执行捷径。

### 3.5 可重复、可诊断
每次运行固定记录平台版本、模块包版本、浏览器版本、环境、用户、组织、账套、用例版本、数据配方版本和执行时间。

### 3.6 人工治理
模型生成的场景和用例先进入草稿/待评审状态。未经审批不得进入正式回归套件。

## 4. 范围

首期范围：
- 采购模块示范接入；
- 通用浏览器运行时和页面适配机制；
- 用例、依赖、数据配方、断言和报告；
- 后续模块可复用的模块接入机制；
- 跨模块集成测试的基础契约。

暂不承诺：
- 全 ERP 所有模块一次性覆盖；
- 生产环境执行；
- 无人审核的任意破坏性操作；
- 通过数据库直接核验所有数据；
- 对 ERP 内部实现进行代码级测试。

## 5. 成功标准

平台是否成功，不以“采购跑通”单一指标判断，而以：
1. 采购作为首个模块可端到端运行；
2. 第二个模块接入时无需复制平台核心；
3. 模块包可独立版本化和评审；
4. 跨模块链路可组合已有模块资产；
5. 报告能区分模块测试与集成测试；
6. 失败可定位到页面动作、业务步骤、断言或数据准备环节。
