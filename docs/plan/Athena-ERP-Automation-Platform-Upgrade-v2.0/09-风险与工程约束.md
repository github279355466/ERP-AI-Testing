# 09 风险与工程约束

## 1. 环境与数据安全
- 仅允许对明确配置的测试环境执行。
- 启动执行前检查目标域名白名单，防止误连生产环境。
- 测试账号凭据通过环境变量或安全配置注入。
- 报告和日志必须脱敏。
- 数据创建使用运行 ID 前缀或其他唯一性策略。
- 清理动作必须来自显式 cleanup policy，不得自动推断并删除。

## 2. 写操作安全
- 新增、修改、审核、撤审、删除必须作为显式动作类型。
- 动作注册表定义允许的动作、参数 schema、风险级别和重试安全性。
- 非幂等动作失败后不得盲目重试。
- 删除/审核/撤审等高影响动作需要用例审批标记和运行配置授权。
- 每个写动作记录开始时间、结束时间、页面对象、目标单据标识和结果。

## 3. Playwright 稳定性
- 优先使用 role/label/placeholder/testid 定位。
- 禁止依赖脆弱的绝对 XPath 或 nth-child 作为默认策略。
- 对定位器执行唯一性校验。
- 使用业务状态等待，避免固定 sleep。
- 失败时采集 screenshot、trace、URL、页面标题和相关 DOM 片段（注意脱敏）。
- 重试策略必须区分导航/查询等安全动作和写动作。

## 4. 模型使用边界
- 模型可辅助抽取 PRD、生成候选场景和用例草稿。
- 模型输出必须经过 schema 校验。
- 模型不得自行批准用例。
- 模型不得直接执行任意脚本。
- 对来源不明的业务规则必须标记待确认。
- 执行引擎只接受经过验证的结构化执行计划。

## 5. 可维护性
- 平台核心与模块包分离。
- 通用适配器必须有独立测试。
- 模块包使用独立版本。
- 重大契约变化通过迁移脚本和 ADR 管理。
- 不为尚未验证的远期需求过度设计微服务。
