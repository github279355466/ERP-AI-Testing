# 05 模块接入与集成测试规范

## 1. 新模块接入：M-ONBOARD

采购完成 P0-P6 后，销售、应收、应付、库存等模块不再重走平台建设阶段，而走以下接入流水线：

| 接入步骤 | 工作内容 | 复用的平台能力 | 模块新增资产 |
|---|---|---|---|
| M1 资料登记 | 指定模块 PRD 根目录、版本和范围 | PRD Scanner | source-index |
| M2 知识建模 | 扫描并抽取实体、字段、流程、规则 | Knowledge Engine | knowledge |
| M3 页面映射 | 识别菜单、列表、表单、弹窗和控件 | Browser/Page Adapter | page-mappings |
| M4 场景用例 | 生成草稿、追溯来源、人工评审 | Scenario/Testcase Engine | scenarios/testcases |
| M5 数据配方 | 定义基础资料和上游单据创建顺序 | Data Engine | data-recipes |
| M6 套件编排 | 组织模块回归套件和依赖 | Dependency Engine | test-suites |
| M7 执行验收 | 在测试环境执行、断言、报告 | Execution/Assertion/Report | execution evidence |
| M8 模块发布 | 固化版本、兼容性和已知限制 | Governance Engine | module release |

### 新模块接入的工作量原则
- 复用平台代码，不复制平台引擎。
- 复用通用控件适配器。
- 新模块特有控件才新增适配器扩展。
- 新模块业务规则只进入该模块知识模型/用例。
- 发现平台通用能力缺失时，先形成平台缺口单，再评估是否升级核心。

## 2. 采购作为首个模块

采购包的职责是提供采购业务资产，例如：
- 采购 PRD 来源索引；
- 供应商、品号、仓库等资料关系；
- 采购单据页面映射；
- 采购流程场景；
- 测试用例；
- 采购数据配方；
- 采购模块套件。

采购不得拥有自己的独立 Browser Engine、通用报告引擎或通用依赖引擎。

## 3. 第二模块接入演练

P6 必须安排一个小范围第二模块演练（建议销售或库存，取决于 PRD 和页面成熟度）：
- 新建模块目录和 manifest；
- 指定 PRD 目录；
- 运行同一 PRD Scanner；
- 使用相同知识模型 schema；
- 生成一个最小场景和用例；
- 复用已有页面控件；
- 执行最小 UI smoke test；
- 输出接入成本和平台缺口。

演练目的不是完成第二模块全量测试，而是证明平台真的可扩展。

## 4. 跨模块集成测试：I-TEST

集成测试包只表达跨模块业务链路，引用模块包的资产。

示例：采购到应付（候选流程，必须以实际 ERP 流程为准）
1. 准备供应商、品号、仓库；
2. 创建并审核采购订单；
3. 依据系统流程执行到货/入库；
4. 创建或生成应付立账单据；
5. 执行付款或核销（按权限和业务范围）；
6. 查询应付余额/单据状态；
7. 校验上下游单据关系和关键金额。

示例：销售到应收
1. 准备客户、品号、仓库；
2. 创建销售订单；
3. 执行出货/销售出库；
4. 创建或生成应收立账；
5. 执行收款/核销；
6. 校验应收余额、单据状态和关联关系。

示例：采购到库存
1. 执行采购入库；
2. 查询库存；
3. 校验对应品号/仓库的可观察库存变化。

## 5. 集成包契约

集成包至少包含：
- `integration.yaml`；
- 引用的模块包 ID 和兼容版本范围；
- 端到端业务目标；
- 跨模块步骤；
- 模块间数据传递映射；
- 端到端断言；
- 清理策略；
- 失败传播策略。

禁止把同一个模块的业务页面步骤复制到集成包中。集成包应复用模块动作/用例，必要时增加跨模块协调步骤。

## 6. 报告分层

报告类型：
- 模块报告：只统计一个模块包；
- 集成报告：统计完整跨模块链路，同时显示各模块子阶段；
- 回归总览：聚合选定模块和集成包，但保留独立统计维度。

不得把多个模块的报告简单拼接后称为集成测试报告。
