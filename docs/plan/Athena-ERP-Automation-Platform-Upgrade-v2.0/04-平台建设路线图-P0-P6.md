# 04 平台建设路线图：P0-P6

## 阶段总览

| 阶段 | 名称 | 目标 | 主要产物 |
|---|---|---|---|
| P0 | 现状盘点与架构基线 | 识别已有成果，制定迁移方案 | 现状报告、差异矩阵、迁移计划 |
| P1 | 平台骨架与契约治理 | 建立模块化仓库、schema、版本机制 | 平台骨架、契约校验、AGENTS.md |
| P2 | PRD 与业务知识引擎 | 可扫描任意模块资料并产出知识模型 | PRD 扫描器、知识模型 |
| P3 | 场景/用例/依赖编排引擎 | 从知识模型生成可评审测试资产 | 场景、用例、DAG、Dry-run |
| P4 | 浏览器与数据准备引擎 | 建立通用 Playwright 运行时和 UI 造数 | Browser Engine、页面适配、数据配方执行 |
| P5 | 执行、断言与报告引擎 | 端到端运行用例并形成证据报告 | 执行器、断言器、报告 |
| P6 | 采购示范模块验收与平台固化 | 用采购验证通用性并修复平台缺口 | 采购模块包、验收报告、扩展指南 |

> 阶段顺序是平台能力建设顺序，不是每个模块都要重新走一遍的流程。P6 采购通过后，其他模块进入 M-ONBOARD。

## P0：现状盘点与架构基线

任务：
1. 盘点当前仓库、分支、依赖、脚本、配置、文档和测试。
2. 识别原 Phase 1/2/3 已有成果及其真实职责。
3. 把原成果映射到新架构：保留、适配、迁移、废弃。
4. 找出采购模块特有逻辑混入平台核心的位置。
5. 检查现有 Playwright 是否已有登录、菜单、页面对象、截图、trace、等待、重试机制。
6. 识别测试环境账号、组织、账套和数据隔离要求；不得输出密码到报告或仓库。
7. 形成风险清单和按优先级排序的迁移计划。

交付：
- `docs/upgrade/P0-AS-IS.md`
- `docs/upgrade/P0-GAP-MATRIX.md`
- `docs/upgrade/P0-MIGRATION-PLAN.md`
- `docs/upgrade/P0-DECISIONS.md`

验收：
- 关键目录和入口均有盘点结果；
- 原阶段成果逐项映射；
- 每项给出保留/重构/迁移/废弃理由；
- 未经人工确认不改动核心代码。

## P1：平台骨架与契约治理

任务：
1. 建立目标目录结构，优先渐进式迁移，不做无收益的大规模重写。
2. 建立 `AGENTS.md`，明确 Codex 的全局规则和阶段边界。
3. 建立 Module Manifest、Scenario、TestCase、Page Mapping、Data Recipe、Execution Report schema。
4. 建立 schema validator 和示例模块包。
5. 建立平台/模块/集成包版本兼容检查。
6. 建立配置加载、日志、错误分类和运行 ID。

验收：
- 空白示例模块可通过契约校验；
- 非法字段、缺失字段、版本不兼容能被拒绝；
- 采购资产可以逐步迁入新契约；
- 单元测试覆盖关键校验路径。

## P2：PRD 与业务知识引擎

任务：
1. 扫描指定 PRD 根目录，支持递归读取和文件类型清单。
2. 对文件建立索引，记录文件路径、版本/修改时间、章节、页码或段落定位。
3. 抽取业务对象、字段、状态、流程、规则、校验、角色权限和上下游关系。
4. 形成术语表、实体关系、流程模型、规则目录和来源追溯。
5. 对冲突、缺失和歧义建立待确认清单。
6. 允许按模块增量扫描，不能每次全量重建。
7. 生成结构化知识模型，并保留原始来源引用。

验收：
- 可指定任意模块 PRD 目录；
- 扫描结果有来源定位；
- 重复扫描可识别变更；
- 不确定内容标记待确认，不自动变成正式规则；
- 采购模型能由当前 PRD 资料生成。

## P3：场景、用例与依赖编排引擎

任务：
1. 基于知识模型生成候选场景和用例草稿。
2. 用例支持前置条件、步骤、数据配方引用、断言和来源追溯。
3. 建立依赖 DAG，支持拓扑排序、循环检测、失败传播。
4. 支持按模块、业务流程、风险和覆盖范围组织测试套件。
5. 建立评审/审批状态治理。
6. 提供 Mock/Dry-run：展示计划，不连接 ERP、不启动浏览器、不创建数据。
7. 生成供后续执行层消费的执行计划。

验收：
- 每条正式用例都有来源依据；
- 未审批用例不能进入正式套件；
- DAG 对依赖排序正确，循环依赖能被识别；
- Dry-run 不触达 ERP；
- 失败传播和阻塞状态符合规则。

## P4：浏览器与数据准备引擎

任务：
1. 抽象 Playwright Browser Session、登录态、页面导航、截图、trace。
2. 建立 Athena 页面适配层和通用控件适配器。
3. 页面映射从模块包加载，禁止采购流程写死在浏览器引擎。
4. 支持主数据选择控件：客户、供应商、品号、仓库、部门、人员等 UI 查询选择。
5. 支持表格、弹窗、日期、下拉、树、附件上传等控件适配。
6. 建立 Data Recipe 执行器，按依赖顺序通过 UI 创建数据。
7. 建立唯一性策略、运行标识、幂等检查、清理策略和造数审计。
8. 增加失败截图、trace、页面快照和定位器诊断。

验收：
- 浏览器基础能力可在独立 smoke test 验证；
- 至少覆盖采购示范流程所需控件；
- 所有业务数据创建都通过 UI；
- 造数动作可追踪、可识别重复运行；
- 页面定位失败时提供诊断，不静默跳过。

## P5：执行、断言与报告引擎

任务：
1. 按执行计划调度用例和依赖。
2. 支持串行优先、受控并发、超时、取消、重试策略。
3. 重试不得重复执行不可幂等的写动作；必须定义动作级重试安全性。
4. 断言引擎采集预期值、实际值和来源。
5. 统一结果状态和失败分类。
6. 生成 HTML/JSON/Markdown 报告。
7. 报告包含模块、套件、用例、步骤、断言、耗时、证据、数据准备和版本信息。
8. 支持按模块和集成链路汇总。

验收：
- 一次运行可生成完整、可追溯报告；
- 失败步骤有截图/trace；
- 报告能区分数据准备失败和业务断言失败；
- 重试策略不会造成重复创建或重复审核；
- 相同输入和版本组合可复现执行计划。

## P6：采购示范模块验收与平台固化

任务：
1. 将采购作为第一个完整模块包接入。
2. 至少覆盖一条采购主流程及关键异常/边界场景，具体范围以 PRD 和页面能力为准。
3. 验证供应商、品号、仓库等基础资料的 UI 选择与造数。
4. 验证采购单据新增、查询、修改、审核/撤审等已批准动作。
5. 验证依赖、断言、证据和报告。
6. 识别采购专属逻辑，确保其不污染平台核心。
7. 输出“新增模块接入指南”和第二模块试接入演练。

验收：
- 采购模块包可独立加载、校验和执行；
- 平台核心不包含采购专属字段/流程分支；
- 第二模块试接入只需新增模块资产及必要适配器扩展；
- 报告中能识别平台版本、模块包版本和用例版本；
- 采购测试结果由真实 UI 执行产生，不得用 Mock 结果冒充。

## 阶段闸门

每阶段完成后必须：
1. 运行自动化单元测试和契约测试；
2. 输出变更清单和架构偏差；
3. 更新文档与版本；
4. 生成阶段验收报告；
5. 等待人工批准后进入下一阶段。
