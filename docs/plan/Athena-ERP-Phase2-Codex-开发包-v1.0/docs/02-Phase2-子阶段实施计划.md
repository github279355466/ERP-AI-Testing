# Phase 2 子阶段实施计划

## P2.0 — 现状审查与安全门禁

**目标：** 明确代码现状、Phase 1 输入、测试环境边界，确保不会误连生产环境。

工作项：
- 仓库技术栈和目录审查
- Phase 1 冻结模型版本识别
- ERP 环境配置与白名单
- 生产环境阻断
- 高风险操作默认关闭
- runId、manifest、日志脱敏、证据目录
- Windows 运行基线和脚本

退出条件：
- 无授权时无法连接 ERP
- 生产环境配置必定被阻断
- 运行信息可追踪
- 凭据不落日志/版本库
- Phase 1 输入版本明确

## P2.1 — 浏览器、会话、登录与导航

**目标：** 稳定打开测试环境、登录并到达指定页面。

工作项：
- Browser/Context/Page 生命周期
- 超时和重试策略
- 登录态检测
- 登录失败、会话过期处理
- 导航配置
- 截图、Trace、console/pageerror、URL、title
- 证据脱敏和保留策略

退出条件：
- 在授权测试环境完成连续多次登录和导航验证
- 登录失败可诊断
- 会话过期不误判为业务页面成功
- 失败证据完整且无明文凭据

## P2.2 — 通用控件适配器

**目标：** 建立可复用的控件操作能力。

控件优先级：
1. Input / Textarea
2. Button
3. Dropdown / Select
4. Date
5. Modal
6. Lookup
7. Grid
8. Tab
9. Tree

每个适配器必须具备：
- 明确输入参数与返回结果
- 可配置定位策略
- 可见/可用/只读/禁用检查
- 操作前后状态检查
- 超时与错误上下文
- 单元或 fixture 集成测试

退出条件：
- 所有本阶段范围内适配器测试通过
- 真实 ERP 上至少验证采购订单用到的 Input、Button、Lookup、Grid、Dropdown/Date（以实际页面为准）
- 不存在只靠固定坐标的核心操作

## P2.3 — 页面对象与知识模型映射

**目标：** 将通用控件组合为可维护的 ERP 业务页面对象。

工作项：
- Phase 1 冻结模型加载
- 页面/字段/控件模型版本检查
- Page Object 基类
- 采购订单页面对象
- locator 配置和页面映射
- 页面侦察与差异报告
- 未映射字段、未知控件、模型冲突管理

退出条件：
- 页面对象不硬编码全局业务规则
- 页面关键字段和控件有映射证据
- 真实页面侦察结果已记录
- 差异均已分类，不静默丢弃

## P2.4 — 采购订单端到端 UI 技术验证

**目标：** 证明底座能通过 UI 完成一个受控业务闭环。

建议最小范围：
- 登录
- 导航采购订单
- 新增测试订单
- 通过 Lookup 选择供应商和品号
- 填写明细
- 保存
- 重新查询
- UI 读取字段并断言
- 采集完整证据
- 测试数据追踪和清理策略演练（清理动作须单独授权）

首轮不强制审核/撤审/删除/过账。只有业务负责人确认必要且风险门禁已实现后，才增加这些操作。

退出条件：
- 真实 ERP UI E2E 成功
- 保存后重新查询并断言关键字段
- runId 与单据标识关联
- 失败证据完整
- 没有使用 API/MCP/SQL 绕过 UI
- 数据清理策略经人工确认

## 阶段执行规则

- 每阶段：开发 → 自动化测试 → 验收报告 → 人工评审 → 下一阶段。
- P2.0/P2.1 可在无 ERP 凭据时完成大部分框架与模拟测试，但真实环境项标记未验证。
- P2.2 控件 fixture 测试不能替代真实 ERP 控件验证。
- P2.3 页面映射必须使用实际页面侦察结果。
- P2.4 必须在用户明确授权的非生产环境执行。
