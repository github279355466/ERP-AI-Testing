# P1 缺陷回归固化清单（2026-11-10）

## 1. 目标与原则

- 一个缺陷 = 一条可复跑用例，修复后只跑对应用例 + 一条主链路即可确认收敛。
- 固化分三级：**A 文档级**（现状，人工按步骤复跑）→ **B 平台用例级**（`business-modules/purchase/testcases` + flow）→ **C 门禁级**（CI 定时回归）。
- 当前先完成 A，B 需为每条缺陷补一个 flow（`src/modules/purchase/flows.ts`）。

## 4. 建议固化方式

### 4.1 短期（本轮已具备）

- 按第 3 节表格人工复跑，每条记录 `run-id`、截图或 JSON 证据到 `artifacts/<run-id>/`。
- 复跑顺序：DEF-12 → DEF-20（同一链路）→ DEF-18 → 其余单点。

### 4.2 中期（推荐）

- 在 `src/modules/purchase/flows.ts` 为每条缺陷补 flow：
  `purchase-rtnout-take-check`、`purchase-rtn-other-price-check`、`purchase-price-npe-check`、`purchase-price-date-check`、`purchase-arr-approve-check`。
- 在 `business-modules/purchase/testcases/` 建同名 YAML，`status: reviewed`，纳入 `test-suites`。
- 执行：`node dist/cli/platform-run.js run --module purchase --case <ID> --allow-write`。

### 4.3 长期

- 将上述用例编入 `SUITE-PURCHASE-P1-REGRESSION`，在每次版本发布前由 `platform:plan:validate` + 批量执行完成回归。

## 5. 修复后的验收口径

- 缺陷用例由 failed/blocked → passed，且主链路（订单→到货→入库→退货→出库）冒烟通过。
- 状态类缺陷必须同时校验“提示信息”和“数据状态”，不得只凭 toast 判定。
