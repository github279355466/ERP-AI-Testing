# 07 Codex 总控执行指令

将以下内容完整复制给 Codex。先让 Codex 阅读本开发包全部文件，再开始 P0。

---

你现在负责升级现有 Athena ERP 自动化测试项目。请先完整阅读本开发包中的所有 Markdown 文件，并将它们视为本次升级的产品章程、架构目标、契约规范、阶段路线图和验收基线。

## 一、你要建设的是什么

目标是建设一套可扩展的 Athena ERP 自动化测试平台，而不是采购模块专用脚本。

总体结构必须保持三层：
1. Platform Core：通用扫描、知识建模、场景用例、依赖、浏览器、页面适配、数据准备、执行、断言、报告、治理。
2. Business Module Packs：采购、销售、库存、应收、应付、生产等模块独立接入。
3. Integration Test Packs：采购到应付、销售到应收、采购到库存等跨模块业务链路。

采购只是第一个示范模块。后续模块必须复用平台核心，不得复制 Phase 1-P6 重新建设。

## 二、技术和业务约束

- 当前目标环境：`https://athena-test.digiwincloud.com.cn/`
- 当前业务操作必须通过 Playwright 浏览器 UI。
- 不得通过 ERP OpenAPI、MCP、SQL 直接查询或写入业务数据。
- 测试数据准备也必须通过 UI。
- 不得将采购业务字段、流程、页面选择器写死到通用平台核心。
- 未经评审批准的场景/用例不能进入正式执行套件。
- 删除、审核、撤审等动作必须在用例中显式声明，并保留审计轨迹。
- 不得把密码、Cookie、Token 写入仓库或日志。
- 不得执行任意模型生成 JavaScript；只允许调用受控动作注册表。
- 不得静默忽略定位器不唯一、依赖缺失、版本不兼容或断言失败。

## 三、第一步只做 P0

现在只执行 P0“现状盘点与架构基线”，不得提前开始 P1-P6，不得大规模重构或删除现有成果。

请完成：
1. 检查当前工作区所有项目文件、目录、脚本、配置、依赖、测试和文档。
2. 找到此前 Phase 1、Phase 2、Phase 3 的全部产物；若不在当前仓库，明确记录缺失，不得假设不存在。
3. 将旧成果映射到新架构组件和 P0-P6 阶段。
4. 对每项成果给出：保留、适配、迁移、重构或废弃建议及理由。
5. 识别采购专属逻辑与通用平台逻辑的边界问题。
6. 识别当前 Playwright 页面对象、登录、导航、控件、截图、trace、等待、重试能力。
7. 检查 PRD 目录的读取方式和文件类型覆盖，不要要求用户逐个上传 PRD。
8. 识别测试环境配置、账号、组织、账套、数据隔离和清理风险；不要读取或打印明文密码。
9. 输出 P0 报告和下一阶段迁移计划。
