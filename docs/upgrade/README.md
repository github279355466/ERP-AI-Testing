## 2. 阅读顺序

1. 先读 `P0-AS-IS.md` 了解“现在是什么”。
2. 再读 `P0-GAP-MATRIX.md` 了解“离目标差什么”。
3. 再读 `P0-MIGRATION-PLAN.md` 了解“怎么迁、先迁什么”。
4. 用 `P0-RISK-REGISTER.md` 和 `P0-DECISIONS.md` 确认风险与需要人工拍板的事项。
5. 用 `P0-ACCEPTANCE-REPORT.md` 核对 P0 是否达到验收标准。
6. 再读 `P1-IMPLEMENTATION-PLAN.md` 与 `docs/acceptance/P1-ACCEPTANCE.md`，决定是否授权 P2。

## 3. P0 的硬边界

- 未连接 ERP，未启动浏览器，未执行任何 Playwright 业务用例。
- 未执行保存、删除、审核、反审核、结账、过账、作废等写操作。
- 未修改任何现有源码、配置、知识库或测试资产；只新增 `docs/upgrade/` 下的 P0 文档。
- 未把任何账号、口令、Token、Cookie 写入文档。
- 未把“Phase 2 局部跑通”写成“采购平台已验收”；Phase 2 P2.4 仍为部分通过。

## 4. 当前一句话结论

P0 结论：现有项目具备“PRD 静态建模 + Playwright 只读/受控写入底座 + 采购单证页面对象”的可用基础，但仍是“采购示范脚本集合 + 两个并存的子系统”，采购逻辑进入 CLI、诊断、页面映射和 PRD 关系/场景等平台核心位置。P1 已建立三层骨架与契约治理，采购实现仍留在 legacy，等待 P4/P6 迁移。
