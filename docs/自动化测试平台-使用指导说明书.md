# Athena ERP 自动化测试平台使用指导说明书

- 版本：1.0
- 日期：2026-11-10
- 适用对象：测试负责人、测试执行人员、模块开发、平台运维、验收评审人
- 依据：平台 1.0.0 发布基线、P1–P6 验收、P7 发布与回滚演练、2026-11 采购域实测结果

## 1. 平台定位

平台用于 Athena ERP 的页面级自动化测试，采用三层架构：

```text
Platform Core（平台核心）
  ├─ 契约 / 运行器 / 断言 / 证据 / 报告 / 数据配方 / 场景编译
Business Module Packs（业务模块包）
  ├─ base / foundation / purchase / ar / ap
Integration Test Packs（集成测试包）
  └─ purchase-to-ap
```

核心不写业务逻辑；业务选择器、字段规则、用例、数据配方归属模块包；跨模块链路归属集成包。

## 3. 可交给平台测试的范围

| 适合 | 不适合 |
| --- | --- |
| 列表/详情只读校验、字段必填/默认/只读/联动 | 导入导出、字段长度边界、并发重复提交 |
| 单据创建、保存、提交、审核、撤审、作废 | 生产环境写入、跨租户操作 |
| 取价、金额/税额、单位换算、汇率换算 | 未授权的批量删除/结账/过账 |
| 主数据 CRUD 与状态流转 | 需要人工判断的模糊业务规则 |
| 跨单据链路（订单→到货→入库→退货） | 纯接口/数据库测试（平台不做） |

## 5. 如何安排测试计划

### 5.1 计划分层

| 层级 | 周期 | 内容 |
| --- | --- | --- |
| 年度/季度 | 季度 | 模块覆盖目标、平台能力目标 |
| 版本计划 | 每个 ERP 版本 | 变更范围、回归范围、验收标准 |
| 批次计划 | 1–2 周 | 一个模块或一条链路，可独立验收 |
| 用例计划 | 每日 | 按用例编号执行、证据、缺陷 |

### 5.2 模块分级

| 级别 | 模块 | 策略 |
| --- | --- | --- |
| A 级（重点） | purchase、foundation | 全字段规则 + CRUD + 链路 + 回归 |
| B 级（扩展） | base、ar、ap | 先只读冒烟，再补字段规则与写入 |
| C 级（后续） | 销售、库存、生产 | 复用模板，先建包再排期 |

### 5.3 测试类型矩阵

| 类型 | 目标 | 频率 |
| --- | --- | --- |
| 冒烟 | 页面可打开、列表可读、关键字段可见 | 每次发布 |
| 字段规则 | 必填/默认/只读/联动/计算/唯一 | 每批次 |
| CRUD/状态 | 新增、编辑、失效、生效、删除 | 每批次 |
| 业务链路 | 取价→订单→到货→入库→退货→出库 | 每版本 |
| 数据一致性 | 金额、税额、数量、单位、汇率、库存 | 每链路 |
| 回归 | 已修复缺陷 + 主链路 | 每次修复后 |

### 5.4 优先级规则

- P0：阻断主链路、数据错误、越权；当日处理。
- P1：核心单据/取价/库存不可用；当前批次内修复并回归。
- P2：单功能不可用或有绕行；排入下一批次。
- P3：文案/交互一致性；进清单，不阻塞发布。

### 5.5 批次计划模板

| 字段 | 内容 |
| --- | --- |
| 批次编号 | 如 `PUR-PRC-2026W46` |
| 目标 | 一句话说明本批次验证什么 |
| 范围 | 模块、页面、单据、字段域 |
| 不测范围 | 明确排除项 |
| 前置数据 | 供应商、品号、价格、仓库、单据 |
| 环境 | 环境/租户/运营单元/账号来源 |
| 准入条件 | 缺陷已修、数据就绪、授权到位 |
| 用例清单 | 用例编号与优先级 |
| 证据要求 | 截图、DOM、请求、错误码 |
| 产出 | 报告、缺陷单、回归结果 |
| 退出标准 | 通过率、P0/P1 清零、未覆盖项说明 |

### 5.6 排期建议

| 周 | 内容 |
| --- | --- |
| W1 | 修复回归：P0 缺陷 + 取价/单位/汇率 |
| W2 | 采购取价矩阵 + 外币/单位换算 |
| W3 | 采购单据链路（订单→到货→入库） |
| W4 | 退货/出库链路 + 批号/储位 |
| W5 | 基础管理字段规则扩展 |
| W6 | base/ar/ap 从只读扩到 CRUD |
| W7 | 集成包 purchase-to-ap 填充 |
| W8 | 全量回归与阶段验收 |

## 6. 如何执行测试计划

### 6.1 执行前检查

1. `npm run platform:health`：确认 runtime/config/schemas/modules/artifacts/CDP 全部通过。
2. `npm run platform:validate`：确认契约与模块包有效。
3. 确认测试环境、租户、运营单元、登录态。
4. 确认写操作授权与数据前缀（当前 `QA26`）。
5. 确认本批次用例、数据、证据目录。

### 6.2 执行流程

```text
建包/映射 → 用例 → 数据准备 → 静态校验 → 真实 UI 执行 → 证据 → 报告 → 缺陷 → 回归
```

1. **建包/映射**：在 `business-modules/<module>/` 维护 `page-mappings`、`field-rules`、`testcases`。
2. **用例**：一条规则一个用例，编号 `FR-<单据>-<类型>-<字段>`；P1 必须有正例+反例。
3. **数据准备**：使用 `QA26` 数据；新增数据登记到 `config/test-data/qa26-master-data.json`。
4. **静态校验**：`platform:module`、`platform:integration`、`platform:plan:validate`。
5. **真实 UI 执行**：通过平台运行器或模块流程执行；写操作需 `--allow-write` 与写入配置。
6. **证据**：每个失败用例保留截图、DOM/请求、错误码；证据目录 `artifacts/<run-id>/`。
7. **报告**：生成 `report.md` / `report.html` / `results.json`。
8. **缺陷**：按 S0–S3 登记，关联用例、单据号、证据。
9. **回归**：修复后只跑失败用例 + 关联主链路，再跑批次冒烟。

### 6.3 只读与写入

- 默认只读：`config/athena.config.json`。
- 写入：`config/athena.write.config.json`（`readOnly=false`、`allowWrite=true`），且需当次明确授权。
- 审核、撤审、作废、过账等高风险动作必须逐项确认，不得默认开启。

## 8. 数据管理

| 项 | 规则 |
| --- | --- |
| 命名 | `QA26` 前缀，编码可读（如 `S-QA26-EUR`、`QA26-M001`） |
| 保留 | 默认保留，不自动清理 |
| 登记 | 新增主数据登记到 `config/test-data/qa26-master-data.json` |
| 隔离 | 只用测试环境、测试租户、测试运营单元 |
| 清理 | 按依赖倒序：价格→批号→采购信息→存货信息→品号→客户→供应商→群组→仓库→单位 |

## 9. 证据与报告

```text
artifacts/<run-id>/
  results.json
  report.md
  report.html
  shots/
  dom/
  logs/
```

- 失败必须有截图 + DOM/请求 + 错误信息。
- 证据统一脱敏，不落 token/Cookie/账号口令。
- 报告结论必须区分 UI 成功、业务成功、持久化成功。

## 10. 缺陷管理

| 级别 | 定义 | 处理时限 |
| --- | --- | --- |
| S0 | 数据损坏、越权、不可恢复 | 立即停止写操作，当日升级 |
| S1 | 核心链路不可用 | 当日升级，阻塞发布 |
| S2 | 单功能不可用或需绕行 | 当前批次修复并回归 |
| S3 | 文案/交互一致性 | 进清单，排期修复 |

缺陷单必须含：编号、页面、复现步骤、实际/期望、严重度、证据、关联用例、数据标识。

## 12. 当前限制与风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 模块包全部 draft 0.1.0 | 不能作为正式发布模块 | 先试点，逐模块升 approved |
| base/ar/ap 仅只读 | 通用性不足 | 先补字段规则与 CRUD |
| 集成包 steps/assertions 为空 | 跨模块链路不可执行 | 先填 purchase-to-ap |
| 8 项未关闭缺陷 | 采购/基础管理有阻塞 | P0 先回归 |
| 单价整数精度（OBS-11） | 外币小数价无法精确验证 | 先用整数价，精度单独立项 |
| 到货库存换算（OBS-12） | 库存数量可能错误 | 优先确认并回归 |
| `platform:validate` 仅覆盖 purchase/foundation/template | base/ar/ap 未纳入契约校验 | 扩展校验清单 |
| 无 CI nightly | 回归依赖人工触发 | 补流水线与定时任务 |

## 16. 个人使用模式（推荐）

### 16.1 三种使用方式

| 模式 | 谁写计划/用例 | 适合场景 | 可复用性 |
| --- | --- | --- | --- |
| A 一句话全托管 | 我生成计划、用例、数据、执行、报告 | 个人日常、单作业验证、探索性测试 | 中（可后续固化） |
| B 自己写用例、平台执行 | 你写 YAML/规则，平台跑 | 已稳定作业、回归套件、团队协作 | 高 |
| C 混合 | 首次我生成，后续你维护并平台回归 | 大多数正式作业 | 高 |

个人使用优先选 **A**，需要长期回归的作业再升级为 **C**。

### 16.2 一句话触发模板

```text
测试【模块/作业】：
范围【表头/明细/CRUD/状态/取价/链路】，
写入【只读 / 允许 QA26 写入】，
数据【QA26 / 新建】，
输出【报告 + 缺陷清单】。
```

示例：

```text
测试采购订单作业：表头+明细字段规则、CRUD、审核撤审、取价，
允许 QA26 写入，输出报告和缺陷清单。
```

收到这句话后，我会自动完成：

1. 读取页面知识与现有资产，确认 workItemCode 与字段。
2. 生成/更新批次计划（`docs/plan/`）。
3. 生成/更新模块资产：`page-mappings`、`field-rules`、`testcases`。
4. 准备或复用 `QA26` 数据。
5. 校验模块包与计划（`platform:module`、`platform:plan:validate`）。
6. 真实 UI 执行，保存证据与 run id。
7. 输出报告、缺陷清单、未覆盖项。
8. 保留数据，登记到 `config/test-data/qa26-master-data.json`。

### 16.3 你只需要做三件事

| 事项 | 说明 |
| --- | --- |
| 确认范围与规则口径 | 例如“失效允许、删除禁止”“阶梯左闭右开” |
| 授权写操作与数据前缀 | 例如“允许 QA26 写入并保留” |
| 验收报告 | 看结论、缺陷、未覆盖项，决定是否进入下一批 |

### 16.4 平台侧“发布”是什么

平台目前没有独立 Web 发布台，发布 = 资产入库 + 契约校验 + 可执行：

```bash
# 1. 资产入库（business-modules/<module>/ 下）
#    page-mappings / field-rules / testcases / data-recipes

# 2. 校验模块包
npm run platform:module -- --path business-modules/purchase

# 3. 编译/校验计划
npm run platform:plan:compile -- --module purchase
npm run platform:plan:validate -- --module purchase

# 4. 执行
node dist/cli/platform-run.js run --module purchase --case <CASE-ID> --allow-write

# 5. 报告
# artifacts/<run-id>/report.md / report.html / results.json
```

个人使用时，第 1–5 步可由我一次完成；你只需要确认第 3 步的用例范围和写入授权。

### 16.5 什么时候不要用“一句话”

| 场景 | 建议 |
| --- | --- |
| 新模块、无页面知识 | 先做一次页面探索，再生成资产 |
| 业务规则有歧义 | 先确认口径，再生成用例 |
| 生产环境或高风险写操作 | 必须逐项确认，不建议全托管 |
| 需要清理数据 | 先给清理方案与依赖顺序 |

### 16.6 建议的个人节奏

- 每天一句话跑 1 个作业，当天出报告。
- 每周挑 1–2 个高频作业，固化为 `testcases/*.yaml` 并纳入回归。
- 每月跑一次模块回归，更新模块状态与缺陷清单。
